# SlayTheList Feature Ideas

Collect feature ideas and improvements here. Add freely, prioritize later.

---

## Ideas

- Make a version that runs on Linux (for testers)
- First-time user tip / onboarding: suggest daily predictions as a practice (e.g. "Did you know you can make predictions for the day? It's a great way to calibrate your intuitions." — offer on first interaction or in a tips section)
- Background music: default ambient/focus music that plays while the app is open, with controls to toggle or swap track
- Screenshot recognition for task completion evidence (take a photo/screenshot to prove you did the thing)
- Hard-locked tasks with friend as fallback unlocker (friend can unlock for you if you're stuck)
- Celebrating another person's achievements gives both parties gold
- Prediction calibration gives recurring gold returns: track how well-calibrated a user is over time (e.g. Brier score or hit rate by confidence band) and pay out a passive gold multiplier/bonus based on their calibration quality — good forecasters earn more gold per prediction resolved, creating an ongoing incentive to make predictions regularly and set honest confidence levels
- Multiplayer / social gameplay via modded game integration: show other users' bases/progress inside a shared game world (starting with Terraria). Let friends see each other's productivity progress reflected in-game — e.g. your completed todos build out your base, and you can visit others' bases
- Chrome tab / video blocking: block specific Chrome tabs or video playback based on productivity state. Should be achievable via screenshot detection (already in the app) or by defining processes and using a Chrome extension API to control tab access
- Social value alignment: explore whether SlayTheList's social features (accountability partners, shared predictions, collaborative goals) can meaningfully contribute to coordination problems — could well-calibrated prediction markets among friends surface better collective decisions?
- Proper double-clickable installer that bundles/downloads Node.js and all dependencies — zero-setup install experience for non-technical users
- Encouragement / celebration feature: positive feedback and celebration moments when completing tasks, hitting streaks, or reaching milestones — make finishing things feel good
- Android app: native or hybrid mobile app so SlayTheList is accessible on the go
- Friend encouragement / celebrations: friends can encourage (on active entries) or celebrate (on completed entries) each other's goals/habits/predictions. Both parties earn a small gold reward. Limited to ~3 interactions per day to keep it meaningful and prevent spam
- API endpoint to add gold directly (with sound playback). Use case: pair Claude Code ultimate driver mode with SlayTheList. Driver mode runs steppified small actions and computes gold rewards per step (e.g. 1 gold for tiny step, 2 for slightly larger), then calls the API to grant gold + play the sound. User gets the dopamine loop without having to manually log every micro-step as a todo. Could also be done by logging fine-grained steps to SlayTheList itself, but that may need a separate fine-grained view. Recommend pairing this with a shareable cleaned-up version of driver mode for other users.
- Interactive AI overlay with screen-aware chat: an always-available overlay where you chat with an AI that watches your screen (screenshot capture is already in the app) and automatically updates the current task's subtasks as you work. The AI infers what you're doing from the screen, breaks the active todo into live subtasks, ticks them off as it sees progress, and lets you steer/refine via chat. Turns the todo list into a live, self-updating checklist rather than something you manually maintain. Could tie into the gold/driver-mode loop (auto-award gold as subtasks complete) and the existing screenshot recognition idea.
- Mindustry integration (open-source game as the gold sink): mod Mindustry (open source, GPLv3, base-defense + factory genre, fits the "maintain and defend a persistent base" desire) so SlayTheList gold translates into in-game resources/units. Architecture: SlayTheList stays a separate process talking to the mod over an API; an auto-download script (or bundled installer as "mere aggregation") gets the game+mod onto users' machines. Licensing summary (checked casually, verify assets licensing before shipping): the mod and any modified game code must be published open source (GPL), but that doesn't restrict monetizing SlayTheList itself (premium features, donations), since GPL doesn't propagate across a process/API boundary and commercial distribution of GPL software is allowed (Anuke sells the GPL game on Steam himself). Free download via anuke.itch.io or GitHub releases. Status: playtested 2026-07-07, verdict probably not. Gold doesn't slot naturally into the resource-routing economy (would have to be bolted on as an extra building cost), the routing setup is too complicated, and the game absorbs hours of attention, which violates the core requirement below. Game looks very pretty though, useful as the visual bar.
- **Design requirement for any SlayTheList game layer** (crystallized from the Mindustry playtest): the game loop must NOT pull the user away from SlayTheList for long stretches. Interaction budget is seconds-to-minutes (spend gold, glance at progress), progression driven by gold income rather than attention, very direct spending ("use gold to buy towers and defend things"), incremental/infinitely-scaling flavor. You're not supposed to spend two hours playing a game with occasional SlayTheList money. This points at idle/incremental shapes and away from integrating real games, whose quality is exactly what makes them absorb time.
- 2D tree-garden visualization: a lightweight 2D scene (no full game integration) where goals/projects grow as trees. Each tree represents a goal, and clicking a tree opens the set of tasks involved in "getting" (growing) that tree — i.e. the todos/subtasks that contribute to it. Completing tasks visibly grows the tree (sapling → full tree), giving an at-a-glance, spatial overview of progress across goals. A simpler, self-contained cousin of the Terraria/modded-game base-building idea.
- Calendar view for goals: a calendar layout that lays out goals (and their tasks/deadlines) across days/weeks/months. See what's due when, when goals were started/completed, and plan ahead by placing goals on dates. Could surface deadlines (`deadlineAt`), completion dates, and habit check-ins on a unified timeline.
- Calibration-driven combat / prediction betting (autobattler + visitable base): a combat layer where the game economy runs on *calibration*, not just task completion — this is the "why not just use Habitica" answer, since Habitica has no calibration substrate. Core pieces:
  - **Bet gold on predictions with a proper scoring rule.** Payout for a binary prediction with confidence `f` and outcome `o` (1=hit, 0=miss): `payout = stake × (1 − 2·(f − o)²)`. This is the quadratic/Brier rule, so reporting your *true* probability maximizes expected gold — overconfidence loses gold in expectation. The economy itself trains calibration; no policing needed. Keep confidence continuous for scoring; snap to buckets (50/60/75/90/99) for display. Stake is a volatility knob and doesn't corrupt the honesty incentive.
  - **Two bet types, scored separately.** (1) *World predictions* — outcome not controlled by user → real calibration, feeds Brier score. (2) *Goal/commitment bets* (via `targetTitle`) — user controls the outcome → Beeminder-style anti-akrasia device, tracked in a separate "commitment" ledger, NOT mixed into Brier (otherwise you inflate calibration by only betting on gimmes you control).
  - **Visitable base / character sheet.** When others visit, show *skill* separately from *outcome/luck*: Brier/calibration score (+ a reliability curve: your 70%-confidence calls actually hit ~68%, dot sits near the diagonal), net gold earnings, and resolved-prediction volume/streak. e.g. "312 predictions resolved · Brier 0.14 · +4,200 gold" with the curve underneath — a social object no other app can render.
  - **Combat should *eat* the prediction system, not sit beside it** (autobattler à la Super Auto Pets / Oaken preferred over Slay-the-Spire deckbuilder, because async snapshot PvP is native to autobattlers: visitors battle a stored snapshot of your deck+stats — no live opponent, deterministic resolution from deck+seed, fits existing cloud-social infra). Gold from predictions/todos buys cards/units; calibration quality becomes a build-defining stat. Murphy-Jitsu failure-modes could become pre-empted debuffs/enemies. Supersedes/absorbs the simpler "calibration gives recurring gold returns" idea above. Rationale: aesthetic (dark+gold) + calibration instrumentation are the real moats vs Habitica; combat is fun-to-build but redundant unless fused with calibration.
- Daily persistent battle / idle base (incremental or tower-defense style): your base is engaged in a continuous, real-time battle (or mining operation) that runs throughout the day. Core loop:
  - **Gold earned from todos has an immediate in-battle payoff.** The moment you earn gold, you can spend it on upgrades/units/defenses for today's battle — possibly from a parallel budget so the main gold balance isn't exhausted (experimental: gold *rate* unlocks things rather than gold being consumed).
  - **Slow-loss pressure instead of hard failure.** Without input you don't (or only very slowly) lose ground — the battle is always on, but the stakes are "am I advancing?" not "did I wipe?". Earning gold at a steady rate (e.g. ~1 gold/hour from doing todos) is what maintains the run and pushes you forward to beat enemies and reach harder tiers over the day.
  - **Time-based, always running.** Progresses in real time while the app is open; skips/fast-forwards elapsed time when it wasn't open (idle-game offline catch-up).
  - **Income rate as the key stat.** The rate you earn gold matters, not just the total — sustaining a rate maintains and advances the run, making productivity-per-hour directly legible in the battle.
  - **Build non-visual first.** Prototype the simulation/economy concepts (tick loop, upgrade costs, enemy tiers, loss rate, offline skip) without graphics to validate what feels right before any rendering. Genre candidates: incremental/idle, tower defense.
  - **Likely visual shape: 2D horde-survivor lane defense (Age of War style).** Monsters stream in from the right, your upgradeable base sits on the left, turrets/defenses in between. A single lane is probably *easier* than grid tower defense: positions are 1D scalars, no pathfinding, no placement grid — and "distance pushed / survived" maps naturally onto the day-long run. Animation can be cheap (Super Auto Pets style): static sprites + transform tweens (bob, squash-on-hit, white flash, particle puffs), no walk cycles or skeletal animation needed. Assets: Kenney CC0 packs already in `frontend/web/public/assets/` (incl. a 3D tower-defense kit; his 2D top-down Tower Defense pack has ~300 sprites with turrets); for frame-animated monsters, itch.io free packs (Pixel Frog, LuizMelo's Monsters Creatures Fantasy) and OpenGameArt LPC sprites exist, but static+tween avoids the dependency. Tower defense proper (grid + path + targeting) is the fallback shape if the lane feels too thin. Relates to the arena combat autobattler (round-based, session-scoped) but is a different shape: day-scoped, continuous, driven by gold *income* rather than discrete battles.
- Agent-relay social updates: since the app's social tab isn't in anyone's natural flow (WhatsApp is), let the AI agent surface friends' progress in-flow instead — e.g. Claude Code mentions "Marcus hit his goals yesterday" during a session. Design rule behind it: social features should produce artifacts that travel (screenshots, streak images, agent mentions) rather than destinations inside the app
- Weekly goals with big gold payout: pick one main goal for the week (e.g. finish a work project or a submission) that pays out a large gold reward when achieved — a weekly-scale layer above daily todos/predictions (from Marcus)
- Shared streaks (Duolingo/Snapchat style): display how many consecutive days both partners completed their todos, shown as a flame/streak counter on the social view. No extra gold needed, the visible shared streak is the motivator (from Marcus)
- Joint todos: todos shared between two people that only pay out gold once both have checked them off (from Marcus)
- Staged game plan: lane defense first, card meta on top (2026-07-07 discussion). The deck-builder incremental and the horde-survivor lane defense stack as development stages of one game instead of competing. **Stage 1**: day-scoped lane defense with plain generic units — continuous gold sink (spend-and-glance: gold buys turrets/upgrades, income rate = battle progress), tiny asset needs (few static sprites + tweens, board/card aesthetic like Super Auto Pets rather than world aesthetic), validates whether gold-income-into-defense-power feels good. **Stage 2**: the placeable units become *cards* — your lane loadout is a deck, gold buys card packs (bursty sink alongside the continuous one), NPC ladder tiers/ascensions give incremental scaling, async friend-visit battles slot in per the autobattler bullet. Defers the 10-20-card-art problem until the economy is proven with placeholders; if art stays hard, generate the set with an image model under one locked style spec (consistency from the generator, not curation) or commission a bounded one-time set. Comparison axes used: core loop, gold sink shape (continuous vs bursty), interaction budget, shareable artifact, content scaling. Deck-builder risk to design against: deck-fiddling is a stealth time sink — cap run frequency (e.g. one ladder run per hour/day) so progression stays gold-driven, not attention-driven. Both stages must respect the seconds-to-minutes design requirement above.
- Habitica integration: sync with Habitica via its public API — e.g. mirror todos/habits both ways (completing a task in either app checks it off in the other), and/or translate SlayTheList gold events into Habitica rewards (or vice versa). Lets users keep Habitica's social features (parties, quests) while using SlayTheList as the primary driver. Open questions: which direction is source of truth, and how gold ↔ Habitica gold/XP map without double-rewarding
- Reuse a previous prediction when making a new one: when creating a prediction, offer a picker of previously made predictions to re-make (autofilling title, and optionally confidence/stake as a starting point). Most predictions are recurring ("I'll finish the day's todos", "I'll be in bed by 23:00"), so retyping them daily is friction. Should be searchable/sorted by recent or most-repeated, and ideally show the past hit rate for that title so re-making it is also a calibration cue.
- Overlay visible by default on app start: starting the app should always bring the overlay back up, and the toggle hotkey stays the way to hide it again for the rest of the session. Today `showGoldToday` / `showBaseOverlay` are persisted API settings (`desktop/overlay-agent/.../MainWindow.xaml.cs` `ToggleOverlayBar` flips both through `PUT /api/settings/:key`), so hiding the overlay once keeps it hidden across restarts and it's easy to forget it exists. Wanted behaviour: hidden is a session state, not a sticky one — on startup the overlay shows regardless of how the last session ended. Open questions: reset both settings to on at API/agent startup vs. keep the persisted setting and add a separate session-scoped "hidden" flag (so the web checkboxes still mean what they say), and whether a user who deliberately unchecks the overlay in Settings should be respected across restarts while a hotkey-hide is not.
- **Dynamic spatial overlay — the AI points at your screen and verifies you did it** (ambitious end-state of `set_current_step`; future direction, 2026-08-12). Today the overlay's current step is one line of *text* the agent writes, and nothing checks whether it happened. The ambitious version makes the whole screen the canvas in both directions:
  - **Markers, not sentences.** Instead of "open the settings modal and turn on autostart", the agent draws a highlight ring / arrow / numbered pip *on the actual pixel location* of the thing to click, in a click-through always-on-top layer over whatever app you're in. Multi-step tasks become a sequence of markers that advance as you go. Text is the fallback for things that have no on-screen location ("write the email"), not the primary channel.
  - **Screenshot-verified completion.** The agent takes a screenshot (capture already exists in the app), compares against what it expected to change, and only then ticks the step off — closing the loop the current step deliberately leaves open. This is the "screenshot recognition for task completion evidence" idea above, but automatic and per-step rather than a manual proof photo.
  - **Verification is what mints gold.** Once completion is *observed* rather than self-reported, the `doneAt` field already sitting unused in the stored current-step shape becomes real, and a verified step can pay out (micro-gold per step, real gold per task) without the user logging anything. Driver mode stops needing the user as the reporting channel.
  - **Hard problems to design against**, in rough order of nastiness: (1) *locating things* — needs either an accessibility-tree read (UIA on Windows gives real element rects, far cheaper and more reliable than vision) or a vision model returning coordinates, with the tree as primary and vision as fallback; (2) *latency and cost* — a screenshot round-trip per step is slow and expensive, so verification should be event-triggered (window changed, file saved, git commit) rather than polled, and markers must survive window moves/scroll or they point at nothing; (3) *false "done"* — a verifier that ticks things off wrongly is worse than no verifier, since it pays gold for work not done and corrupts the one thing the economy is built on (see the whole "both resources minted by real work only" rule in The Crawl); (4) *privacy* — continuous screen reading is a much bigger ask than a text line, so it needs to be explicitly opt-in, per-app scoped, and visibly indicated while active; (5) *the noise constraint from `set_current_step` applies doubly* — an overlay that draws on your screen while you work can ruin the screen it is drawn on. Markers should be sparse, quiet, dismissable, and off by default.
  - **Incremental path** so it isn't one giant leap: current step (done) → step *lists* with manual ticking → event-triggered verification for the cheap deterministic cases (file exists, test passes, commit made — no vision at all) → UIA-located markers for one whitelisted app → general vision-located markers. Each stage is useful alone. Absorbs and supersedes the "interactive AI overlay with screen-aware chat" idea above, which is the chat-shaped version of the same thing.
- Badge / achievement icons on the profile summary (Habitica-style): show a row of earned-badge icons on your login/summary screen and shared social profile as a condensed, at-a-glance reflection of your progress in the game (combat/autobattler) and base-building parts. Instead of making friends open your full base or combat deck to gauge how you're doing, badges act as compact identifiers — like Habitica's character gear / house cosmetics that signal progression. Badges would be awarded for milestones (base build-out tiers, combat wins/rank, streak/calibration achievements) and render as small icons next to the gold/habits summary. Pairs with the existing self-view + shared-profile work (habit grid, daily gold log): the daily log shows *recent activity*, badges show *accumulated standing*.

## In Progress

- The Crawl — overlay dungeon run (started 2026-08-09): a Slay-the-Spire-shaped card crawl that lives in the overlay panel, 5 floors x 2 rooms ending in a boss worth 10 real gold. Answers the "seconds-to-minutes" design requirement by making the game literally unable to advance without real work. **Two resources, both minted by productivity only, neither by playing**: ENERGY = the gold you earned *today* (a mirror of the ledger, not a deduction — playing never lowers the balance; expires at midnight, never banks), and LOCKS = a todo the agent pins via `lock_crawl_on_todo`, which freezes the run entirely until it is `done`. A todo finished in the last hour grants +3 momentum damage, so the reward lands right after you do the thing. Built: pure `shared/crawl-engine` (41 tests, `npm run test:crawl`, incl. `pacing.test.ts` asserting a reference player clears all 5 floors on 5 seeds for ~129 energy ≈ 5 good days); `crawl_state` singleton table with load-time defaulting; `GET /api/crawl` + play/end-turn/reward/restart/lock endpoints; `get_crawl` + `lock_crawl_on_todo` MCP tools; shared `CrawlView` used by both `/crawl` and `?panel=crawl`; `crawlToggleHotkey` setting. **The Crawl is fully standalone, not part of the Base/Friends bar** (user request 2026-08-09): it has no button on the native pill and none in the web overlay bar, because a dungeon run is not a status dropdown like Base or Friends. It is its own always-on-top window reached by hotkey (or `/crawl` in a browser), with its own drag grip and its own remembered position in `crawl-window.json` — it does not dock to the bar, so toggling the bar never moves it. The two hotkeys are therefore fully independent: the crawl hotkey shows only the run (writing no settings at all, never pulling the gold chip and bar on screen) and the overlay hotkey shows only the gold chip and bar (never taking the run away). Dragging needs `WM_NCLBUTTONDOWN`/`HTCAPTION` rather than WPF's `DragMove()`, because these windows are `WS_EX_NOACTIVATE` so they never steal focus, and WebView2 swallows every mouse event in the client area — hence the explicit 22px grip strip. **Three design rules found by simulation, each fixing a run that was unwinnable or unfair** — (1) the enemy only swings in RESPONSE to a played card, never on a clock, because drawing required ending a turn and ending a turn cost HP, so a low-energy player was ground to death for being away; (2) HP resets fully every room — energy spans the run, HP spans one fight, or a stretch of irregular play quietly dooms you; (3) the hand REFILLS each turn rather than drawing one, because draw-1 caps sustained output at ~one card per swing and made the 120 HP boss arithmetically unwinnable at any energy. Enemy HP climbs steeply (that is the energy cost) while attack climbs gently (capped against the 40 HP pool). Deliberately no shop and no between-run setup: rewards are a one-click pick-1-of-3, which is the specific answer to the "deck-fiddling is a stealth time sink" risk below. **Open**: balance is sim-verified but not human-playtested (the reference policy banks energy before opening a turn — a player who dribbles their last 2 energy into a boss will lose, and the UI does not yet teach that); no sound; no 3D. Next per the 2026-08-09 decision: keep the 2D card presentation, then prototype a three.js first-person corridor between rooms (step-based, Grimrock-style, render only while the panel is open) and compare. Unity was considered and rejected — it cannot render inside the WebView2 panel, so it would mean a second always-on-top process plus duplicating docking/sizing/capture-exclusion/hotkey/API plumbing outside TypeScript, ~50MB+ of package, and continuous GPU cost for a window that sits open while you work.

- Lane defense Stage 1 (started 2026-07-08): headless deterministic sim in `shared/defense-engine` (`npm run test:defense`). Design v2 (kill-count model, same day): each tier is a horde of `killsPerTier` monsters ground down at a rate ∝ DPS ratio; the horde is always at the walls — any deficit bleeds the base (no front-position abstraction); clearing a horde summons a stronger generation (tier ladder ×1.07) AND the horde creeps +0.3%/h from run start, so banked advantage erodes overnight and the "morning bleed until you've done today's todos" dance is guaranteed; collapse = full reset (A/B settled by user 2026-07-08: "regen better than damage is bad design — just reset on death"): no safe state at all (`chipBleedFloor: 0.006` — the horde always chips ≥0.42%/h even at advantage; user: "holding isn't good either") so damage STICKS and HP is the run's lifespan (~1 day idle, ~10 days played well); death wipes to tier 1 on the meta floor, then `reclaimKillBoost` (8×) sprints you back to ~bestTier within a day (~30min/tier, LaneTheater plays it as fast carnage) while scaling past your best stays normal-paced; kill rate is super-linear in power ratio (`killRateExponent: 2`, cap 6×) so overpowering a stage visibly rushes the next one; `killsPerTier: 100` for a visibly moving slain counter (granularity only). Knockback mode still exists behind `POST /api/defense/config {deathMode}` (default reset, toggle UI removed). 1D lane kept (2D map placement would violate the seconds-to-minutes budget); lazy fast-forward `advance(state, now)` in 1-min ticks = always-running + offline catch-up, no background process. Pacing (asserted in `pacing.test.ts`, tuned for ~25g "good day" income): tier-up ~every 0.75-0.95d, first collapse after ~3 weeks of steady play then fast re-climb, idle collapse ~53h, fresh zero-input fall day ~2.2, meta reclimb ~3× faster. Iso base at `/base` shelved untouched (route still exists but is no longer linked from the home nav — the "Base" tab now opens `/defense` instead, per user 2026-07-08). Also done (2026-07-08): `defense_state` SQLite table (id=1 real, id=2 sandbox) with lazy fast-forward on read, endpoints `GET /api/defense-state`, `POST /api/defense/upgrade` (real mode spends real gold via `spendGold`, ledgered private), `POST /api/defense/sandbox` (skip time / grant practice gold / reset — sandbox only); `/defense` page (CSS-drawn lane: keep, towers, front line; `LaneTheater.tsx` = decorative client-side skirmish loop — monsters walk in, lunge at the line, take tower bolts with hit-flashes, pop on death, respawn to keep the screen populated; tempo driven by sim kill rate/advantage, pure decoration over the deterministic engine; upgrade/battle/legacy panels; sandbox toggle at `/defense?sandbox=1`); Defense tab on home nav. Event sounds done (2026-07-08): reuses `lib/combat/sfx` synth — fanfare on tierUp, defeat drone on baseDestroyed (only for events <5min old, so offline catch-up doesn't blast stale dooms), sparkle on upgrade; Sound on/off toggle in topbar persisted to localStorage; deliberately no ambient battle noise (app sits open during work). Next: playtest + balance pass, then Stage 2 (cards) per the staged plan bullet.
